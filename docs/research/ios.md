# Hevier on iOS: research and plan

Repo state read: `expo ~57.0.28`, `react-native 0.86.3`, Android-only (`app.json` has no `ios.bundleIdentifier`, no `ios/` folder, CNG).
Date of research: 2026-11-07. Nothing in the repo was modified.

Provenance tags used below:
- [src] read in the actual npm package source (`expo-widgets@57.0.28`, `@expo/ui@57.0.26`) downloaded to the scratchpad.
- [docs] fetched from docs.expo.dev (SDK 57 pages, `llms.txt`).
- [know] Apple platform behaviour from my knowledge; developer.apple.com pages are JS-rendered and could not be fetched. Every [know] item has a Simulator check in section 4/6.

## 0. Verdict in 10 lines

1. JS, SQLite, sync, camera, routing, UI already run on iOS. Only the two Kotlin modules, the notification permission, USB sync and a few Info.plist strings are Android-only.
2. iOS has no ongoing notification. The equivalent is a Live Activity (lock screen banner + Dynamic Island) with `Button(intent:)` actions (iOS 17+).
3. The countdown needs no background work: `Text(timerInterval:countsDown:)` and `ProgressView(timerInterval:)` are drawn by the system. Rest-over sound/buzz = a local notification scheduled at `restEndsAt`.
4. SDK 57 ships `expo-widgets@57.0.28` (widgets + Live Activities written in JS with `@expo/ui`). It is the fastest path but has two blockers for Hevier (4.1).
5. Recommended path: hand-written SwiftUI WidgetKit extension (generated by `@bacons/apple-targets`) + the two existing local modules gain an `apple` half in Swift. Same JS API, same JSON contract as Android.
6. Keep `modules/workout-notification` and `modules/home-widgets` as the cross-platform façade (`platforms: ["android","apple"]`). `hooks/useWorkoutNotification.ts` and `lib/refreshHomeWidgets.ts` barely change.
7. Free Apple account: install on own iPhone for 7 days, Live Activity probably OK, App Groups (needed by widgets) must be tested first. TestFlight and EAS device builds need the paid program.
8. This Mac has Xcode 26.6 but no Simulator runtime installed and no CocoaPods: `xcodebuild -downloadPlatform iOS` and `brew install cocoapods` first.
9. Simulator verifies: Live Activity (lock screen + Dynamic Island), button intents, widgets, timelines, deep links, sync against the Mac. It cannot verify: sound/haptics, Local Network prompt, APNs, free-account signing.
10. Effort: about 7 PRs, roughly 6-9 working days including a 1-day Swift/signing spike up front.

## 2. Live workout notification on iOS

### 2.1 What the Android module does (contract to preserve)
`ShowOptions` (types/notification.ts): `title, setText, restText, restEndsAt(ms), restTotal(s), image(file://), setButtons[], restButtons[]`. Events: `onAction {id: complete|skip|minus15|plus15, restEndsAt?, restTotal?}`.
Behaviour worth copying:
- Between sets: title = exercise, text = "Set 2/4 - 80 kg x 8 reps", button Complete Set.
- Resting: countdown + bar, text "Next: Set 2 of 4 (...)", buttons Skip / -15s / +15s.
- `RestController` acts on the rest buttons natively and immediately, then tells JS the new end time (not "+15 again"), and de-dupes JS echoes (`merge`, `ECHO_WINDOW_MS`).
- Service switches back to the set line by itself at rest end, with 2 buzzes + `pr.wav`, even when JS is paused.
- Tap opens `hevier://log-workout`. Not shown for backdated workouts.

### 2.2 iOS mapping
| Android | iOS |
|---|---|
| Foreground service + ongoing notification | `ActivityKit` Live Activity (lock screen banner, Dynamic Island compact/expanded/minimal). Requires `NSSupportsLiveActivities = YES`. Started with `Activity.request` while the app is in the foreground [know] (the workout starts in-app, so fine). |
| Chronometer + progress bar | `Text(timerInterval: start...end, countsDown: true)` + `ProgressView(timerInterval: start...end, countsDown: true)`: the system animates them with zero updates [know]; both exist in `@expo/ui` 57 (`src/swift-ui/Text`, `ProgressView` have `timerInterval`) [src]. |
| `setButtons`/`restButtons` actions | `Button(intent: LiveActivityIntent)`, iOS 17+. Different layout per state, driven by ContentState. |
| Native `RestController` | Same maths in Swift, executed inside the intent's `perform()`. |
| Rest-over buzz + chime (service alive) | Live Activity cannot play sound. Schedule `UNTimeIntervalNotificationTrigger` at `restEndsAt` with `pr.wav` (<=30 s, bundled in the app via the expo-notifications plugin `sounds`), cancel/reschedule on Skip/+-15/hide. Local notifications fire when the app is suspended or killed. [know] |
| Switch to set line at rest end | `ActivityContent(state:, staleDate: restEndsAt)`; the view shows the set line when `context.isStale` (the system re-renders at the stale date without the app). [know, verify in Simulator] |
| Wake lock | Not needed, nothing to keep alive. |
| Exercise still (`image`) | Write the circular PNG to the App Group container; view loads by path. (Activity payload limit is 4 KB, so no images in ContentState.) [know] |

Limits [know]: one Live Activity max ~8 h active (+ up to 4 h on lock screen), fine for workouts; `Activity.request` only from foreground; updates from the app need the process to be running; user can disable Live Activities in Settings (`ActivityAuthorizationInfo().areActivitiesEnabled` -> use fallback in 2.5).

### 2.3 The hard part: buttons when JS is not running
`LiveActivityIntent.perform()` runs in the app process; iOS starts the app in the background if needed [know]. Android solved the same problem by acting natively first (RestController). Same must be done here.

What `expo-widgets@57.0.28` does [src]:
- `ios/Widgets/AppIntent.swift` `LiveActivityUserInteraction.perform()` only calls `WidgetsEvents.shared.sendNotification(...)` = `NotificationCenter.post`.
- `ios/WidgetsModule.swift` registers the observer in `OnStartObserving(onUserInteraction)`, i.e. only once JS has subscribed. There is no queue.
- `Button onPress` return value updates props only for widgets, not Live Activities.
=> If the app was terminated, the tap launches the process in the background, the intent posts before JS subscribes, the event is lost. With the app merely suspended it works. Not acceptable for "Complete Set" (the main button).

(Voltra 2.4.0 queues events through an App Group for cold launches per its docs, but does not update the activity itself after a press; web docs only partially read, treated as not evaluated further.)

### 2.4 Recommended design (one path)
Swift half of `modules/workout-notification` (new folder `ios/`, podspec, `"apple": {"modules": ["WorkoutNotificationModule"]}`):

```
modules/workout-notification/
  index.ts                      (unchanged API + 2 additions below)
  expo-module.config.json       platforms: ["android","apple"]
  ios/
    WorkoutNotification.podspec
    WorkoutNotificationModule.swift   Function show/hide, Events onAction, drainActions()
    WorkoutActivityController.swift   Activity request/update/end, rest maths (port of RestController.kt), UN notification scheduling
    WorkoutAttributes.swift           ActivityAttributes + ContentState (Codable; copied into widget target)
    WorkoutIntents.swift              CompleteSetIntent, SkipRestIntent, AdjustRestIntent(delta) : LiveActivityIntent
    ActionQueue.swift                 App Group JSON queue of pending actions
```
Widget extension target (one for everything, Live Activity + 4 widgets) lives in `targets/hevier-widgets/` (apple-targets) with `WorkoutLiveActivity.swift` (views only), plus a copy/symlink of `WorkoutAttributes.swift` and `WorkoutIntents.swift` (intent *declarations* must exist in both processes; same type name across modules is the standard ActivityKit practice [know]).

Data flow:
1. JS `showWorkoutNotification(options)` -> module -> `Activity.request` first time, `update` afterwards. `ContentState` = `{title, setText, restText, restEndsAt, restTotal, resting, buttons}` plus `upcoming`.
2. New optional field `upcoming: {exerciseKey, setKey, title, setText, restText, restSeconds}[]` (next 3 sets, computed in `lib/workoutNotification.ts` with the existing `nextSet`/`setValues` by simulating "set done"). Lets native advance state on Complete Set without JS. Android ignores it.
3. Button tap -> intent `perform()` in the app process:
   - Skip/+-15: apply `RestController` maths, update Activity + reschedule rest-end local notification, append `{id, restEndsAt, restTotal, ts}` to the App Group queue.
   - Complete Set: pop `upcoming[0]`, switch state to resting (rest = `restSeconds` of the completed set), schedule rest-end notification, append `{id:'complete', exerciseKey, setKey, ts}`.
4. If JS is alive: module emits `onAction` immediately (same payload as Android) and clears the queue entry. Else JS drains at launch/foreground: `drainActions()` called from `useWorkoutNotification` on mount and on `AppState` 'active'; replays `completeSet(exerciseKey,setKey)` (idempotent: `markSet` returns when `next === set.done`) and `setRest(...)` with the last rest. Then the normal `show()` re-sync reconciles the Activity with the DB.
5. Echo guard: port `merge()`/`sentRests` from `RestController.kt` unchanged.
6. Quiet-after-tap (`QUIET_AFTER_TAP_MS`) and 250 ms redraw throttle are Android view-hierarchy workarounds, not needed.
7. Tap on banner -> `widgetURL(hevier://log-workout)`.
8. Root layout: `Notifications.setNotificationHandler` returning no banner/no sound while foreground (the app already plays the chime in-app), otherwise the rest-end notification doubles it.

JS interface additions in `modules/workout-notification/index.ts` (Android keeps no-ops):
```ts
export interface ShowOptions { /* existing */ upcoming?: UpcomingSet[] }
export function drainPendingActions(): NotificationAction[]   // [] on Android
export function areLiveActivitiesEnabled(): boolean            // true on Android
```
No new package is needed; the repo's convention is `modules/*` with `@/modules/...` imports. If the owner wants `packages/workout-activity`, it is a pure rename.

### 2.5 Options compared (why this one)
| Option | Verdict |
|---|---|
| `expo-widgets@57.0.28` Live Activity (JS views, official, SDK-57 tagged `sdk-57`) | Easiest: no Swift, plugin creates target, App Group, `NSSupportsLiveActivities`, push support. Blockers: (a) button events lost on cold background launch [src]; (b) UI limited to `@expo/ui` components in an isolated JSContext (no imports/closures); (c) `LiveActivityAttributes` is fixed, no `staleDate` use, no native rest maths. Keep as Plan B / throw-away spike. |
| Voltra 2.4.0 (callstack) | Not evaluated beyond docs search; updates after a press still need JS; extra abstraction; Android widgets experimental. Not chosen. |
| `expo-live-activity` 0.4.2 (software-mansion-labs) | Fixed layouts, no custom intents/buttons. Not suitable. |
| `react-native-widget-extension` 0.3.0 | Only scaffolds target, you write Swift anyway; apple-targets is the better scaffold. |
| `expo-notifications` categories only | Cannot show a persistent live countdown; action buttons are hidden behind long-press/expand [know]; on iOS a background/terminated action tap does not run `registerTaskAsync` ("Only on Android..." [docs]). Use only as fallback and for the rest-end alert. |

Fallback when Live Activities are off/unsupported (iOS < 16.2 or user disabled): schedule only the rest-end local notification (category "REST" with Skip / +15s actions via `setNotificationCategoryAsync`, `opensAppToForeground: false` [docs]); no persistent surface. Document it, do not build more.

SDK 57 / RN 0.86 compatibility notes
- Do not add `expo-widgets` in the recommended path, so nothing from it touches RN 0.86. If used as Plan B: `npx expo install expo-widgets` resolves `57.0.28` (npm tag `sdk-57`; `latest` is 58.x, do not install by hand). It depends on `@expo/ui ~57.0.26`; its own devDependencies are `react-native 0.86.3` [src] so it is built against the repo's RN.
- `expo-notifications`: `npx expo install expo-notifications` (tag `sdk-57` = 57.0.26). Needed for permission + `sounds` plugin + foreground handler.
- `@bacons/apple-targets` 5.0.0 (2026-07-17, peer `expo >=52`, needs CocoaPods 1.16.2 and Xcode 16+ [docs]). Published before SDK 57: not verified against SDK 57/RN 0.86, covered by Spike 0 (7.1). If it fails, Plan B is the expo-widgets plugin approach (it is MIT and shows how to add a target, Pod linking and App Group by config plugin).
- Set iOS deployment target 17.0 through `expo-build-properties` `ios.deploymentTarget` (expo-widgets' fallback is 16.4 [src]; the Podfile template default is `16.4`). 17.0 gives interactive intents with no `#available` noise.

## 3. Home widgets on iOS

### 3.1 What exists (contract)
`WidgetData` (types/widgets.ts): `days[]`, `volume{day:kg}`, `cycle{name,step,total,exercises[]}|null`, `recovery: {at, colors{group:hex}}[]`. JS pushes it on app open and on background (`app/_layout.tsx` `HomeWidgets`, `lib/refreshHomeWidgets.ts`). Native computes "today", "this week", current recovery colours itself and books a redraw at midnight or next colour step. Taps open `hevier://calendar`, `hevier://profile`, `hevier://`.
Four widgets: Calendar (month grid, Monday first, workout days bold on disc, today highlighted), Volume (this week / last week kg), Cycle ("n of m", name, exercises), Recovery (front+back body: grey photo clipped to outline, muscle paths coloured at 0.85 alpha).

### 3.2 iOS mapping
| Android | iOS |
|---|---|
| `WidgetStore` SharedPreferences JSON | JSON file `widgets.json` in the App Group container (`FileManager.containerURL(forSecurityApplicationGroupIdentifier:)`). Written by the `home-widgets` Swift module. Not the SQLite file: the Android design already prefers a JSON snapshot and the schema is reused verbatim. |
| `RedrawScheduler` midnight alarm + next colour step | WidgetKit `Timeline`: entries at now, each `recovery[i].at`, and next local midnight; `policy: .after(midnight+5s)`. `WidgetCenter.shared.reloadAllTimelines()` after each `update()`. No alarms needed. |
| RemoteViews layouts | SwiftUI views: `CalendarWidget`, `VolumeWidget`, `CycleWidget`, `RecoveryWidget` (systemSmall/Medium; Recovery systemMedium). One `WidgetBundle`. |
| `BodyRenderer` + `body_paths.json` | SwiftUI `Canvas`/`Shape`. `body_paths.json` uses only absolute `M L C Z` commands (checked), so a ~40-line SVG-path-to-`Path` parser is enough. Reuse the JSON as bundle resource; convert `widget_body_front/back.webp` to PNG (asset catalogs do not take webp; or load webp from the bundle with `UIImage(contentsOfFile:)`, iOS 14+ decodes it). Mirror LEFT shapes with `CGAffineTransform(scaleX:-1 ...)` exactly like `BodyRenderer.kt`. |
| `widget_*` colours (`res/values/colors.xml`) | copy values into a Swift `enum WidgetColors`. |
| Click -> deep link | `.widgetURL(URL(string:"hevier://calendar"))` per widget. |
| Interactivity | none needed (read-only), so no App Intents in widgets. |

Staleness caveat: iOS may delay timeline reloads; entries are precomputed so colour/day changes land on time even if the app is closed; the data itself (new workouts) refreshes whenever the app opens/backgrounds, same as Android.

### 3.3 Options compared
| Option | Verdict |
|---|---|
| `expo-widgets` JS widgets | `updateTimeline` fits the recovery steps well, calendar logic can run in the layout (`environment.date`). But layouts cannot import anything or close over variables, `@expo/ui` has no `Canvas`/arbitrary `Path` view (checked `src/swift-ui/Shapes`: only rounded/ellipse/etc.), so the Recovery body would need pre-rendered PNGs in `widgetsDirectory` (react-native-svg `toDataURL` per step). Workable for 3 of 4 widgets; poor fit for Recovery. Plan B. |
| Hand-written SwiftUI via `@bacons/apple-targets` | Chosen: pixel parity, no runtime JS in the extension, the `targets/_shared`-style sharing and App Group mirroring are first-class [docs]. ~600 lines Swift total. |
| App Group + SQLite directly | Rejected: needs the DB moved to the group container (expo-sqlite supports it, but the sync/restore code paths use `Paths.document/SQLite`), risk to user data for no gain. |

App Group id: `group.com.hevier.app`, declared in `app.json` `ios.entitlements["com.apple.security.application-groups"]` and mirrored in the target's `expo-target.config.js` [docs]. The same group is used by the Live Activity (exercise still PNG, action queue).

## 5. Sync (backup-server) on iOS
- Server speaks plain `http://<pc-ip>:4873` (`lib/sync/pairing.ts baseUrl`). iOS ATS blocks cleartext except exceptions. The bare template Info.plist ships `NSAppTransportSecurity { NSAllowsArbitraryLoads: false, NSAllowsLocalNetworking: true }` (checked in `expo-template-bare-minimum@sdk-57`); `NSAllowsLocalNetworking` covers LAN IPs and `.local`. Verify it survives prebuild by reading `ios/Hevier/Info.plist`; if absent add it via `ios.infoPlist.NSAppTransportSecurity`. Do **not** use `NSAllowsArbitraryLoads` (remote content stays HTTPS-only). `usesCleartextTraffic` stays Android-only.
- Local Network privacy (iOS 14+): connecting to a LAN IP triggers a one-time permission prompt that needs `NSLocalNetworkUsageDescription` [know]. No `NSBonjourServices` (no mDNS, the QR carries the IP). If the user taps Don't Allow, `fetch` fails and `lib/sync/client.ts request()` returns `null` -> `pcNotFound`; add an iOS hint to the `pcNotFound` message ("check Settings > Hevier > Local Network").
- `quietSync` runs 'a few seconds' after every app open (`app/_layout.tsx QuietSync`): on iOS that would show the Local Network prompt out of context on first launch. No change needed: `syncNow` returns `notPaired` before any request when there is no pairing, so the prompt only appears after pairing; confirm once on the device.
- Pairing: `expo-camera` `CameraView` with `barcodeScannerSettings {barcodeTypes:['qr']}` works on iOS; needs `NSCameraUsageDescription` via the plugin [docs]. Camera is unavailable in the Simulator, so test the pair link (4.4) and do the camera scan once on the device. `hevier` scheme is already in `app.json`.
- USB cable sync: `adb reverse` is Android-only. On iOS hide that button; same-Wi-Fi only. Corporate/guest Wi-Fi with client isolation will fail the same way it does on Android.
- `backup-server/README.md`: add an iOS note (same Wi-Fi, allow Local Network; macOS firewall prompt for Node when the server first listens).
- Files: `File.upload(url,{httpMethod:'PUT'})` and `File.downloadFileAsync` are URLSession-backed on iOS and ignore ATS for IPs under `NSAllowsLocalNetworking`; nothing to change in `expoIO.ts`.

### 6.2 Risk list
1. **Signing/App Groups on a free account** (4.2): may force widgets behind the paid program. Mitigation: Spike 0 first; Live Activity does not depend on the group if the action queue falls back to standard `UserDefaults` (intents run in the app process, no sharing needed); only the exercise image and widgets need the group.
2. **App Intents in a CocoaPods static library are not always picked up** by the app's intent metadata [know]. If `LiveActivityIntent` taps do nothing in the Simulator: move intent + attributes sources into the app target (`targets/_shared`, which apple-targets links into the app and all targets [docs]) and have the module observe a `NotificationCenter` name (the pattern expo-widgets itself uses [src]); or adopt `AppIntentsPackage` (Xcode 15.3+/iOS 17.4+ [know]). Decide in Spike 0.
3. **`@bacons/apple-targets` 5.0.0 vs SDK 57/RN 0.86/Xcode 26.6** unverified. Fallback = Plan B (`expo-widgets` plugin and JS views) or vendoring its plugin ideas.
4. **Cold-launch intent**: confirm after `simctl terminate` that `perform()` completes the native work within the system's short background window; keep `perform()` synchronous-light (no DB, no JS wait). All DB work happens later in JS via the queue.
5. **State divergence** between the native-advanced Activity and JS/SQLite (user taps Complete on the lock screen, edits sets in app). Mitigation: queue replay is idempotent by `(exerciseKey,setKey)`; after replay JS always calls `show()` with the DB truth; `upcoming` is rebuilt each time.
6. **Rest-end alert reliability**: local notification sound obeys silent switch/Focus [docs]. Optional: `interruptionLevel: timeSensitive` requires the Time Sensitive entitlement (paid) [know]; skip.
7. **`staleDate` re-render behaviour** is the only way to flip to the set line without background execution [know]. If the Simulator shows it does not flip, do not try to schedule a background update (not reliable); accept the countdown resting at 0:00 with a static "Rest over, Set N next" line.
8. **Widget Recovery rendering cost**: large JSON (up to ~170 steps x ~40 muscle colours) decoded in the extension (memory ~30 MB limit [know]). Pre-trim steps to unique future ones (already done in `recoverySteps`) and cap to 48 entries on iOS.
9. **Apple review / future App Store**: Live Activity must show real activity state; a pure workout timer is fine. Not relevant until paid.
10. **expo-notifications bundle weight and the foreground handler**: forgetting `setNotificationHandler` double-plays the chime in foreground (2.4 step 8).
11. **EAS**: if the owner later uses EAS for iOS, extension credentials (second App ID, App Group) must be provisioned (`eas build` syncs capabilities incl. App Groups with Apple cookies auth, local runs only [docs]). Keep local builds as default.
12. **iPad** (`supportsTablet: true`): Live Activity/widgets work, layouts untested; consider `false` for v1.

### 6.3 Plan B (if Spike 0 kills the Swift route)
Install `expo-widgets@57.0.28` (+ `@expo/ui` pulled in), define `createLiveActivity('Workout', ...)` with `Text timerInterval`, `ProgressView timerInterval`, `Button target=...`, listen with `addUserInteractionListener` in `useWorkoutNotification`, ship Calendar/Volume/Cycle via `createWidget` + `updateTimeline`, and render Recovery as App Group PNGs (`widgetsDirectory`). Accept: buttons only work while the process is alive; the Recovery widget is approximate. Same JS façade, so it can be replaced later.
